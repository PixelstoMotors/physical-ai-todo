mechArm に使っているデータの全体図

小型ロボットアーム mechArm 270 Pi を「iPhone と Unity だけで物を掴ませる」公開プロジェクト Pixels to Motors で、実機がどんなデータを読み書きしているかの全体図。入力（採用した姿勢）→ アーム → 出力（試行の記録）という流れに、最近足した 補正記憶（実機で測ったズレを位置ごとに覚えて、次の狙いを自動で直す仕組み）が加わっている。「イメージ図」で関係を絵で掴み、「全体解説」で実際のファイルの場所と根拠を確認する。

読み方・用語：DAYxxx（下のファイル名などに出る）＝毎日公開している開発ログの通し番号（例：DAY235＝開発235日目）。live＝入力データ、twin＝座標と関節角度を対応づける変換テーブル、real＝実行結果の記録。pose_id＝同じ姿勢を3系統（live/twin/real）で突き合わせる共通ID。approach＝ブロックの手前上空へ行く中間動作、descend＝そこから降りて掴む動作。EMA＝指数移動平均（新しい測定を少しずつ混ぜて更新していく平均）。KIOXIA＝測定データを置いている外付け SSD。件数・行数などデータ増加で変わる数値は載せない。パスは実機とコードで確認済み。

①三系統アーキテクチャ ── live / twin / real

live＝採用JSON（入力）、twin＝descend 時に読む FK テーブル、real＝KIOXIA の試行台帳（出力）。中央の run_pick_place が3つをつなぐ処理。pose_id（赤の破線）は3系統を突合する join key。補正記憶は二次の学習層で、詳細は ②+ と③。絶対パスは③。

②+実装済みの追従ループ ── 補正記憶 × fk_lookup 実装済み

設計どまりではなく、実機に実装して動いている。 検出位置をいったん 補正記憶（位置→Δ(x,z)・KIOXIA）で block − Δ（検出位置から記憶したズレを引く）に補正してから lookup へ渡す。descend（降りて掴む動き）は fk_lookup が変換テーブルから 6 関節すべてを引く（j1 が一定角を超えるとアームが命令を黙って無視するため、j1≤88° の範囲に絞る）。approach（手前上空への中間動作）は従来どおり。実測した爪先のズレ Δ を EMA（少しずつ混ぜる平均）で記憶へ書き戻し、次試行で読む。X 方向だけ効いていた補正が、6関節で引くようにしたことで Z（奥行き）方向にも効くようになった（爪先の奥行きズレが 25mm 級から 10mm 級へ）。残るのは保持（grip/hold）── 位置は合うが j4 抜け・握り緩みで落とすことがある（④参照）。

コード根拠（誰がどこを読み書きするか＝コードが正）

  • j0_lookup：VALID_PHASES = approach_pick / pick / approach_place / place_withblock / place_noblock。LOOKUP_PHASES から place_noblock を除外（L78）。place_noblock を渡すと ValueError（L258-262・detect 全失敗で XZ→j0 を持たない）。実質 place = place_withblock。pose_id は _load_arc が返す（L269）。
  • run_pick_place：ledger・run JSON とも KIOXIA（LOG_ROOT L142 / LEDGER_CSV_PATH L147）。KIOXIA 未マウントなら run 冒頭で ABORT（L1272-1275）し Mac 内蔵へ書かない（この早期 abort は台帳に追記されない）。descend(pick)は fk_lookup が FK テーブルを実行時に読む（旧記述「FK テーブルは読まない」は撤回）。
  • fk_lookup：FK_LOOKUP_PHASES=("pick",) で descend のみ適用、approach は j0_lookup のまま。_load_fk_table がテーブル読込時に hard limit ＋ J1_SAFE_MAX=88.0 で絞る（j1>88° はアームが命令を黙って無視する（silent reject）ため候補から除外）。補正は _apply_correction が block−Δ を返し、その target を fk_lookup に渡す（補正の渡し方は j0_lookup 時代と同じ・受け手の自由度だけ 1軸→6関節に増えた）。
  • j0_sweep_scan：出力先 DEFAULT_OUTPUT_ROOT（L100）＝ .../dynamic_tracking_limits/logs/j0_sweep/。docstring L28 の ~/r2r2r-scripts/logs/j0_sweep/ は省略表記で、実体は dynamic_tracking_limits 配下。adopted/ への配置は別工程。

twin の構造詳細：列は ee_x,ee_y,ee_z,j0..j5（ee＝Unity 座標 m・関節＝度）。ee は Unity 内のグリッパー先端形状（Brep）の位置で、一般の運動学計算（ikpy ライブラリ等）では再現できない。点の追加は Unity の FKScanner を再実行するしかない。

解決：real は「二重化」していなかった

以前「Mac working v3 と KIOXIA v2 が二重化」と疑っていた件は誤り。~/r2r2r-scripts/ 配下に ledger は 0 件（find 確認）。台帳の実体は KIOXIA の /Volumes/KIOXIA/r2r2r-data/runs/pick_place_ledger_v3.csv 単一で、コード（run_pick_place L147）もここを直書き。KIOXIA 専用・ローカル fallback なし。real は単一ソース・v3で確定。
